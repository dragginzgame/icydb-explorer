# icydb 0.215.5 Bump Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the explorer from `icydb =0.202.1` to `=0.215.5`, adapting to what changed and nothing more.

**Architecture:** Scoped **bump-and-adapt only**, per an explicit decision recorded in `docs/superpowers/notes/2026-07-30-icydb-author-review.md`. Take the new version, fix what the compiler flags, renumber one diagnostic, and map one new `SqlQueryResult` variant through the existing `view` DTO boundary to the frontend. Adopt no new icydb capabilities.

**Tech Stack:** Rust (Tauri 2, `ic-agent` 0.48, `icydb` =0.215.5), React 19 + Vite + Tailwind 4, `cargo test` + Vitest.

## What research already established

Verified directly against the vendored `0.215.5` sources, so the plan states facts rather than asking anyone to re-derive them:

| Surface | Change |
|---|---|
| `SqlQueryResult` | **+1 variant: `ShowConstraints { entity: String, constraints: Vec<EntityConstraintDescription> }`** — the only breaking change |
| `OutputValue` | **Unchanged** — still exactly 24 variants, identical set. `List`/`Map`/`Enum` were already recursive in 0.202.1. |
| Generated perf envelope | **Field-for-field identical** (`icydb-model-0.215.5/src/build/actor/db/sql.rs:229-240`), so the local `SqlQueryEnvelope { result }` mirror still decodes |
| `build_configured_canister!` | Signature unchanged: `($canister_ty:ty, $canister_path:literal, $canister_name:literal)` |
| Introspection diagnostic | `RUNTIME_BOUNDARY_SQL_INTROSPECTION_DISABLED` moved **183 → 179** |
| `icydb` features | New intermediate `query`; `sql = ["query", "icydb-core/sql"]`. `sql-explain` still implies `sql`, so the existing feature list needs no change. |
| Public `SqlQueryEndpointResponse` | **Not shipped.** The envelope is still generated privately per canister, so the local mirror stays and remains correct. |


### Corrected after a full re-audit (2026-07-30)

The table above originally said "`SqlQueryResult`: +1 variant." That came from diffing
variant *names*, which missed payload changes. A full type-body diff found three more
items. Recorded because the first audit's method was the problem, not its diligence:

| Additional change | Real? | Action |
|---|---|---|
| `SqlQueryResult::Ddl` gained `constraint_validation: Option<SqlConstraintValidationOutput>` | **yes** | The `Ddl` arm must destructure it (we map `Ddl` to an error, so binding and ignoring is fine) |
| `Projection(SqlQueryRowsOutput)` → `Projection(RowProjectionOutput)` | **no** — `SqlQueryRowsOutput` was a type alias for `RowProjectionOutput`; the alias is gone, the type is the same, and we never referenced the alias | none |
| **`icydb::design` was removed**; the `#[canister]`/`#[store]`/`#[entity]`/`#[list]` macro surface moved to the new `icydb-model` crate | **yes — blocks the fixture build** | Task 1 Step 5b, below |
| `EntityFieldDescription`, `EntitySchemaDescription` gained accessors (`constraints`, `identity`, `row_layout_*`, `historical_fill*`, `insert_default*`, `insert_omission`, `introduced_in_layout`); `new` signatures changed | **no impact** | Every accessor `view/schema.rs` consumes (`name`, `kind`, `nullable`, `primary_key`, `entity_name`, `primary_key_fields`, `fields`, `indexes`) survives unchanged. Do **not** start consuming the new ones — that is scope creep. |
| `Date::new` / `Ulid::generate()` removed | **yes** | `view/value.rs`'s test helpers need the replacement APIs |

Note `EntitySchemaDescription` now has a `constraints()` accessor, so `DESCRIBE` can
surface constraints too. **Ignore it.** This bump maps the `SHOW CONSTRAINTS` variant
because the compiler demands it; enriching `DESCRIBE` is a separate feature.

`EntityConstraintDescription` (`icydb-core-0.215.5/src/db/schema/describe.rs:269`) is re-exported at `icydb::db` and follows the same private-fields-plus-accessors pattern as the other description types. It has 16 accessors: `id`, `name`, `kind`, `origin`, `validation_state`, `validation_progress`, `field_id`, `index_id`, `relation_id`, `fields`, `index`, `relation`, `target_entity`, `action`, `semantics`, `check_sql`.

## Global Constraints

- `icydb` pinned exactly `=0.215.5` with `features = ["sql-explain"]`, declared **once** in the workspace manifest and inherited via `{ workspace = true }`. Never reintroduce a second declaration.
- Rust toolchain **1.96.0**.
- The app is **read-only**. It must never call `icydb_ddl` or `icydb_update`, and must only use `ic-agent` query calls. There are exactly two network call sites, both `agent.query` — keep it that way.
- **No icydb type outside `src-tauri/src/view/` and `src-tauri/src/sql/transport.rs`.** This bump is the test of that boundary; do not weaken it to make the bump easier.
- Exhaustive matches on `OutputValue` and `SqlQueryResult` — **no `_ =>` arms.** A wildcard would make this bump compile silently and defeat the mechanism that surfaced it.
- Private key material never reaches disk, a log, a panic message, or an `AppError`.
- **User-facing copy must not claim the app enforces read-only access as a security boundary.** The guarantee is that the app calls only `icydb_query`, a query method whose dispatcher rejects mutation statements, and query calls cannot persist canister state.
- No new icydb **capabilities**: **do not** adopt `icydb_schema`, the `integrity` config key, `[canisters.*.schema]`, `EntitySchemaDescription::constraints()`, or any other 0.215.5 feature. Those were explicitly declined.
- **One new crate is approved, and only this one:** `icydb-model = "=0.215.5"`, because `icydb::design` was *removed* from the public `icydb` crate and the macro surface the fixture depends on now lives there. This is adapting to a relocation, not adopting a capability — the macro names are identical. An earlier draft of this plan listed `icydb-model` as declined; that wording was wrong, and the correction is the user's explicit call.

- [ ] **Step 2: Write the failing tests**

**`EntityConstraintDescription` has private fields and no public `new`**, so a struct
literal won't compile from our crate. But it derives `CandidType, Deserialize`
(`icydb-core-0.215.5/src/db/schema/describe.rs:268`), and candid is structurally
typed — so encoding a local mirror with matching field names and decoding it as
`EntityConstraintDescription` constructs a real one in about ten lines.

Do that. It is the only way to cover the accessor mapping in CI, and it catches the
one mistake the serialisation test cannot: a DTO field wired to the wrong accessor
(`origin` reading `kind()`, say) would serialise perfectly and be silently wrong.

Add a helper to `view/schema.rs`'s test module:

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use candid::{CandidType, Decode, Encode};
    use serde::Deserialize;

    /// Mirrors `EntityConstraintDescription`'s candid shape so a real one can be
    /// constructed for tests — its fields are `pub(crate)` and it has no public
    /// constructor, but it derives `CandidType`/`Deserialize`, and candid is
    /// structural. Field names and types must match icydb's exactly or the decode
    /// fails loudly, which is the desired behaviour if icydb changes the shape.
    #[derive(CandidType, Deserialize)]
    struct ConstraintWire {
        id: u32,
        name: String,
        kind: String,
        origin: String,
        validation_state: String,
        validation_progress: Option<candid::Reserved>,
        field_id: Option<u32>,
        index_id: Option<u32>,
        relation_id: Option<u32>,
        fields: Vec<String>,
        index: Option<String>,
        relation: Option<String>,
        target_entity: Option<String>,
        action: Option<String>,
        semantics: String,
        check_sql: Option<String>,
    }

    fn sample_constraint() -> EntityConstraintDescription {
        let wire = ConstraintWire {
            id: 1,
            name: "demo_row_pk".into(),
            kind: "primary_key".into(),
            origin: "declared".into(),
            validation_state: "valid".into(),
            validation_progress: None,
            field_id: Some(0),
            index_id: None,
            relation_id: None,
            fields: vec!["id".into()],
            index: None,
            relation: None,
            target_entity: None,
            action: None,
            semantics: "immediate".into(),
            check_sql: None,
        };
        let bytes = Encode!(&wire).expect("wire encode");
        Decode!(&bytes, EntityConstraintDescription).expect("decode as icydb's type")
    }

    #[test]
    fn a_constraint_maps_each_field_from_its_own_accessor() {
        let dto = constraint_to_dto(&sample_constraint());
        assert_eq!(dto.name, "demo_row_pk");
        assert_eq!(dto.kind, "primary_key");
        assert_eq!(dto.origin, "declared");
        assert_eq!(dto.validation_state, "valid");
        assert_eq!(dto.fields, vec!["id".to_string()]);
        assert_eq!(dto.semantics, "immediate");
    }
}
```

Every asserted value is distinct, so a field wired to the wrong accessor fails rather
than coincidentally matching.

**Check `ConstraintWire`'s field list and types against
`icydb-core-0.215.5/src/db/schema/describe.rs:269-285` before running** — the
`validation_progress` field's real type is
`Option<ConstraintValidationProgressDescription>`, and `candid::Reserved` is used
above only because `None` is all this test needs. If the decode fails, report the
candid error verbatim; it means the shape differs from what's written here, which is
worth knowing precisely.

- [ ] **Step 5b: Adopt `icydb-model` so the fixture compiles again**

`icydb::design` no longer exists in 0.215.5 (verified: `pub mod design` is present in
`icydb-0.202.1/src/lib.rs` and absent in `0.215.5`). The macro surface moved to the new
`icydb-model` crate, whose `prelude` re-exports the **same** names — `canister`,
`entity`, `enum_`, `list`, `map`, `newtype`, `record`, `set`, `store`, `validator`
(`icydb-model-0.215.5/src/lib.rs:43-56, 68-72`).

Three edits, no design change:

1. Workspace root `Cargo.toml`, under `[workspace.dependencies]`:

```toml
icydb-model = "=0.215.5"
```

2. `fixture-schema/Cargo.toml`, under `[dependencies]`:

```toml
icydb-model = { workspace = true }
```

3. `fixture-schema/src/lib.rs` — replace the single import:

```rust
use icydb_model::prelude::*;
```

**The macro *grammar* also changed, so the attribute lists need updating too.** An
earlier draft of this step said the declarations could be left untouched; that was
wrong — the import swap resolves, then the macros reject the existing arguments. The
grammar below is read from `icydb-model-macros-0.215.5/src/node/`, and the changes are
renames and deletions only: **the fixture's schema semantics do not change.** Same
entities, same fields, same types, same primary key, same index.

**`#[store]`** now accepts exactly `canister = ...` plus `storage(heap())` or
`storage(journaled(...))` (`node/store.rs:15-20,126`). Drop `ident` and `store_name` —
both are gone, and `grep` confirms nothing outside the declaration references
`FIXTURE_DATA`, so the generated static's name is internal:

```rust
    #[store(
        canister = "Canister",
        storage(journaled(
            data_memory_id = 100,
            index_memory_id = 101,
            schema_memory_id = 102,
            journal_memory_id = 103,
        ))
    )]
```

**`#[entity]`** accepts `store`, `version`, `pk`, `index`, `relation`, `typed_adapters`
and the field list (`node/entity.rs:77-97`). There is no entity-level `name` — remove
it if present.

**`field(...)`** takes `name`, `value`, and optionally `default` / `generated`
(`node/field.rs:189-191`). The per-field key moved from `ident` to `name`:

```rust
        field(name = "id", value(item(prim = "Ulid")), generated(insert = "Ulid::generate")),
```

**`Ulid::generate()`** now returns `Result<Self, InternalError>`. It appears in two
places in `fixture-schema/src/lib.rs`, and they need different treatment:

- Inside `generated(insert = "Ulid::generate")` it is a *string* the macro consumes, so
  it may still be valid — icydb's own codegen decides. Try it unchanged first.
- In the hand-written `Default` impls it is a real call and must be updated.
  `src-tauri/src/view/value.rs:184` already handles this by using
  `Ulid::from_bytes([0u8; 16])`; a deterministic value is fine for a `Default` impl and
  arguably better than a random one in a fixture.

**Managed timestamps became opt-in, and must be re-declared.** In 0.202.1,
`icydb-schema-derive`'s entity macro pushed `created_at`/`updated_at` onto **every**
entity unconditionally, with no opt-out — `fixture-schema/src/lib.rs` never declared
them and simply relied on that. In 0.215.5, `Timestamps::field_names()`
(`icydb-model-macros-0.215.5/src/node/entity.rs:35-51`) returns `None` unless the
entity carries a `timestamps` key, so no timestamp fields are generated and the
hand-written `Default` impls fail with `E0560: no field named created_at`.

This is a real field-set change, not a rename — the one place "same fields" does not
hold. **Restore them** on both `#[entity]` declarations:

```rust
    timestamps(created_at(name = "created_at"), updated_at(name = "updated_at")),
```

The macro's own error text confirms the shape: `timestamps(...) requires
created_at(name = "...") or updated_at(name = "...")`.

Restoring is the right call rather than deleting the two lines from each `Default`
impl, even though deleting is the smaller diff. The fixture is this project's
integration-test target; keeping its schema byte-identical across the bump means the
bump is the only variable. Silently dropping two columns would change what
`SELECT *` returns, and any later test difference would be ambiguous between "the
client changed" and "the fixture changed".

**Still stop and report** if a declaration fails for a reason not in the list above —
that would mean semantics changed, not just spelling, and redesigning the fixture's
schema is outside this bump.

Keep `icydb = { workspace = true }` in `fixture-schema/Cargo.toml` if anything still
needs it; remove it only if the compiler says it is genuinely unused.

- [ ] **Step 5c: Adapt the fixture's runtime code to newly-fallible APIs**

The schema crate compiling is not the end of it. `fixture/src/seed.rs` also needs
updating, because the generated `db()` accessor became fallible:
`icydb-model-0.215.5/src/build/actor/db/store.rs:530-533` returns
`Result<DbSession<…>, Error>` where 0.202.1 returned the session directly. The `db!`
macro text itself is unchanged — it still expands to `crate::db()` — so this is a
codegen change, not a macro change.

Four call sites in `fixture/src/seed.rs` need `db!()?` in place of `db!()`.

**A note on when to stop, because earlier drafts of this plan over-applied it.** The
standing instruction to stop and report was written for questions like the managed
timestamps one — where the answer changes what the fixture *models* or what appears on
the wire, and getting it wrong silently corrupts the integration-test target.

It was not meant for mechanical adaptation. **Proceed without stopping** when the fix
is: adding `?` to a call that became fallible, renaming a method or field the compiler
names for you, updating an import path, or replacing a removed helper with its
documented successor — anything where the compiler tells you both the problem and the
answer, and the fixture's schema and behaviour are unchanged.

**Still stop** when a fix would change the fixture's field set, its entity or store
shape, its primary key or indexes, what its candid exports, or any behaviour a test
could observe — or when you cannot tell which category you are in. Say which category
you judged each fix to be in, so the call is reviewable.

- [ ] **Step 5d: Rewrite the fixture's seeding to the new typed write path**

`DbSession::insert<E>(entity) -> Result<E, Error>` is gone. 0.202.1 had it at
`icydb-0.202.1/src/db/session/write.rs:184`; 0.215.5 has no equivalent ergonomic
whole-entity insert on the session facade. This is a shape change, not a rename.

**The `icydb_fixtures_load` contract itself is unchanged** — 0.215.5 still generates
that endpoint and still calls `crate::icydb_fixtures_load`
(`icydb-model-0.215.5/src/build/actor/db/sql.rs:330-333`). Only the function's body
needs rewriting.

Two routes exist. **Take the typed one.**

**Set `typed_adapters` on both `#[entity]` declarations.** The macro then generates
`<Entity>Insert` / `<Entity>Patch` / `<Entity>Replace` structs plus
`TypedWriteAdapter` impls (`icydb-model-macros-0.215.5/src/node/entity.rs:1122-1244`),
gated behind exactly that flag — `entity_typed_adapter_tokens` returns nothing when it
is unset (`entity.rs:1158-1161`), which is why `.insert(...)` currently has no method
to resolve to.

Then seed via `DbSession::bind_typed_entity` → the generated `…Insert` struct →
`execute_trusted_typed_write` (`write.rs:1099, 1128`). **Read the generated struct's
actual field shape before writing the calls** — derive it from
`typed_operation_struct_tokens`, or build once and let the compiler tell you.

The structural alternative — `execute_trusted_structural_insert_batch(entity: &str,
patches: Vec<StructuralPatch>)` (`write.rs:1025`), with patches built via
`session.structural_patch(fields)` and `.field(name, value)` — needs no entity change
but is stringly-typed. Rejected deliberately: this is the integration-test target, and
a mistyped field name there would seed a silently wrong shape that no test in this
repo would catch. Compile-time checking is worth the extra flag.

Setting `typed_adapters` is adaptation, not capability adoption, on the same reasoning
as the timestamps restoration: 0.202.1 provided this write ergonomics unconditionally
and 0.215.5 makes it opt-in. Restoring it keeps the fixture's behaviour identical.

## Self-Review Notes

**Scope coverage.** Every research finding maps to a task or is explicitly a no-op: the pin and diagnostic → Task 1 Steps 1 and 5; `ShowConstraints` → Task 1 Steps 2-4 and Task 2; the unchanged envelope and `build_configured_canister!` → Task 1 Step 6 verifies rather than changes them; unchanged `OutputValue` → nothing to do, and stated so the implementer doesn't hunt; the new `query` feature → no action, since `sql-explain` implies `sql` implies `query`; the unshipped public envelope type → the mirror stays.

**Declined scope is named explicitly in the Global Constraints** — `icydb_schema`, `integrity`, `[canisters.*.schema]` — because an implementer reading only their own task would otherwise see them in 0.215.5 and reasonably think adopting one was an improvement. (`icydb-model` is *not* declined scope — it is the one new crate the Global Constraints explicitly approve, since `icydb::design` was removed from `icydb` and relocated there; an earlier draft of this note listed it as declined, which was wrong.)

**Two deliberate "expect a failure" steps.** Task 1 Step 1 and Task 2 Step 2 both assert a *compile error* as the expected outcome, and both say to stop and report if it doesn't occur. That inversion is the point: those two guards — Rust's exhaustive match and TypeScript's `never` exhaustiveness check — are the mechanism the architecture bet on, and a bump that compiles silently would mean the bet had quietly stopped paying.

**One unknown, resolved in two passes before dispatch.** An earlier draft asked the implementer to check whether `EntityConstraintDescription` has a public `new`. It does not. A second draft therefore left `constraint_to_dto` untested, reasoning that the mapping is branch-free. The pre-flight scan then caught that the type derives `CandidType, Deserialize`, so a ten-line candid round-trip constructs a real one — which is the only way to cover the accessor mapping in CI, and the only way to catch a field wired to the wrong accessor. The plan now does that. Worth recording because the first two answers were both defensible and both wrong.

**Type consistency.** `ConstraintDto`'s six fields are named identically in Rust (Task 1) and TypeScript (Task 2), with the camelCase rename accounted for (`validation_state` → `validationState`). `ResultDto::Constraints` is a struct variant in both, matching the existing `Entities`/`Stores`/`Memory` precedent for the internally-tagged-enum constraint.

## Postmortem

**The bump's purpose was to test one claim, and it did.** Thirteen minor versions of
icydb produced **five** bump-forced compile errors — four inside
`src-tauri/src/view/`, one at `src/App.tsx`'s `never` guard. Both firewall mechanisms
fired by name:

```
error[E0004]: non-exhaustive patterns: SqlQueryResult::ShowConstraints { .. } not covered
error TS2322: Type '{ type: "constraints"; … }' is not assignable to type 'never'
```

Nothing reached the command surface or the frontend uninvited. That property was
asserted in the original design spec and is now evidence rather than belief.

**The cost landed almost entirely on the fixture.** The test canister needed five
layers of migration, each discovered only when the previous one cleared:
`icydb::design` relocated to a new `icydb-model` crate; the macro grammar changed
(`field(ident=…)` → `field(name=…)`, `#[store]` dropped `ident`/`store_name`,
`#[entity]` dropped entity-level `name`); managed `created_at`/`updated_at` became
opt-in; the generated `db()` became fallible; and `DbSession::insert(entity)` was
replaced by a `typed_adapters`-gated typed-write path.

**My research was wrong in a specific, repeatable way.** I audited the icydb surface
that `src-tauri` consumes — `SqlQueryResult`, `OutputValue`, the description types —
thoroughly, twice, including a full re-audit after being caught once. I never audited
the surface the **fixture** consumes: schema macros, the `db!()` session API, seed
helpers. A canister and a client touch nearly disjoint slices of that crate, and
"I audited icydb" quietly meant "I audited half of icydb."

Five estimates followed from that gap, each stated confidently and each wrong:
`icydb-model` is a declined capability (it was required); the swap is three lines (the
grammar changed too); the declarations can be left untouched (they couldn't); `same
fields, renames only` (timestamps had become opt-in); `same entities` (dropping
`#[entity]`'s `name` renamed them).

**The most consequential finding was the one nobody was looking for.** Dropping
`#[entity]`'s `name` attribute changes the SQL-visible entity name to the struct
identifier — `demo_row` became `DemoRow`. I had framed removing that key alongside
genuine no-ops. It broke four of seven live tests, and it directly contradicted the
rationale I had used to justify restoring the timestamps: *keep the fixture's schema
identical so the bump is the only variable*. I achieved that for timestamps and missed
it for names. Nothing in icydb's materials warns of it; a failing test found it.

**What the process caught that a solo pass would not.** The implementer stopped five
times rather than compiling around a problem — twice with an obvious shortcut
available (invent plausible DSL; delete two lines from a `Default` impl for a green
build with a quietly smaller schema). They also declined to route around a safety
classifier, and declined to count an ASCII scan of generated source as the wire check
they had been asked for, decoding the schema fragment with real
`candid::IDLArgs::from_bytes` instead. Reviewers caught that README item 9's promise of
"exactly one version string to bump" had been falsified by the second pin this very
bump introduced, and that `sql/classify.rs` still carried the `readonly = true`
security claim the upstream author had disproved — three of four sites had been
corrected in an earlier phase and that one was missed. Both are whole-branch findings
by construction.

**What to do differently.** Audit the dependency surface *per consumer*, not per
dependency — a canister crate and a client crate share a name and almost nothing else.
Calibrate "stop and report" to the class of problem: it is right for semantics
questions where a wrong guess silently corrupts a test fixture, and wasteful for
mechanical adaptation the compiler has already diagnosed. And when a rationale is
worth stating — "keep the fixture identical" — check every dimension it covers, not
just the one that prompted it.
