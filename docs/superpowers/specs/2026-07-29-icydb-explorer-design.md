# icydb_explorer — Design

**Date:** 2026-07-29
**Status:** Approved

## Purpose

A Tauri desktop app for browsing [icydb](https://github.com/dragginzgame/icydb) databases living inside Internet Computer canisters: pick a canister, see its tables, inspect their schemas, page through rows, and run read-only SQL.

## Feasibility summary

icydb already exposes the surface an explorer needs. Canisters built with the `sql`
feature generate controller-gated endpoints:

- `icydb_query : (text) -> (variant { Ok : SqlQueryResult; Err : Error }) query`
- `icydb_ddl` — DDL statements (not used by this app)
- `icydb_update` — mutations, only generated when `icydb.toml` sets an explicit
  update policy (not used by this app)

`SqlQueryResult` (`crates/icydb/src/db/sql/types.rs`) is a `CandidType` enum whose
variants map directly onto explorer features:

| Variant | Explorer use |
|---|---|
| `ShowEntities` | table list |
| `ShowColumns`, `Describe` | column types, primary keys, constraints |
| `ShowIndexes` | index inspector |
| `ShowStores`, `ShowMemory` | storage and memory stats |
| `Projection` | row grid, paged via `next_cursor` |
| `Grouped`, `Count`, `Explain` | aggregates and query plans |

Row values are typed, not stringified: `RowProjectionOutput.rows` is
`Vec<Vec<OutputValue>>`, where `OutputValue` is a 24-variant enum
(`Ulid`, `Principal`, `Decimal`, `Timestamp`, `Blob`, `List`, `Map`, `Null`, …).
The grid can therefore be type-aware rather than rendering a wall of strings.

Tauri is the right choice specifically because its backend is Rust: it can depend on
the real `icydb` crate and decode responses with
`Decode!(bytes, Result<SqlQueryResult, icydb::Error>)` — the same line
`icydb-cli`'s shell uses. `icydb-cli` is itself a native host binary depending on
`icydb` with `features = ["sql-explain"]`, which confirms the crate compiles off-wasm.
A web or Electron app would have to reimplement all of that decoding in TypeScript.

## Prerequisite: canisters must opt into the SQL surface

icydb's `sql` feature is **not** in default features (`default = []`). As of today
`dragginz/toko` has no `icydb.toml` and does not enable the feature — its built
candid (`.icp/local/canisters/user_hub/user_hub.did`) exposes only `icydb_metrics`
and `icydb_metrics_reset`, no `icydb_query`.

Making a canister explorable requires `features = ["sql"]` on its icydb dependency
plus an `icydb.toml`. The defaults generated by `icydb config init` already match a
read-only explorer:

```toml
[canisters.user_hub.sql]
readonly = true
ddl = false
fixtures = false
update = false

[canisters.user_hub.sql.introspection]
local = true
ic = false
```

Note `introspection.ic = false`: `SHOW`/`DESCRIBE`/`EXPLAIN` default to enabled on
local builds and disabled on IC builds. Mainnet browsing is therefore blind to
schema unless a canister opts in.

**Decision:** rather than block v1 on modifying toko, this repo ships a minimal
fixture canister with the SQL surface enabled, covering the interesting
`OutputValue` variants. It unblocks development immediately, gives integration
tests a stable target that will not shift as toko evolves, and serves as the
reference for enabling the surface on toko later. Enabling it on toko is an
independent follow-up, not step zero.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Target environments | Local first, mainnet later | Introspection is on locally by default; keep the connection layer environment-agnostic so mainnet is config, not a rewrite |
| Access | Read-only | `SELECT`/`SHOW`/`DESCRIBE`/`EXPLAIN` only; smallest surface, safe to point anywhere |
| Transport | `ic-agent` in the Tauri backend | Faster and cleaner errors than shelling out to `icp`; no external binary on PATH |
| Sharded entities | Canister tree, query one leaf | Never invents cross-canister query semantics or lies about where a row lives |
| Canister discovery | Name→id map from `.icp/`, then a per-canister topology walk | Zero manual entry; a forest, not a single root — see "Discovery inputs" |
| Frontend | React + Vite + Tailwind | Matches every other frontend in the user's projects |
| icydb version | Pinned `=0.202.1` | Matches toko's pin; icydb moves fast and `SqlQueryResult` is version-coupled |

## Discovery inputs

An `icp`-managed project keeps everything the explorer needs under `.icp/`, but the
exact layout varies between projects.

**Corrected 2026-07-30 after the final whole-branch review.** The original version
of this table generalized from a single sample (`dragginz/toko`), where the network
and the project are *both* named `toko` — so `toko.ids.json` read as "project name"
when the convention is actually **network name**. It also assumed a project-local
`.icp/cli-home/`, which this repo does not have at all. The layout varies, so
discovery must handle both shapes.

| Path | Yields |
|---|---|
| `.icp/cache/networks/<network>/descriptor.json` | Primary source: `network`, `gateway.{ip,port}`, cached `root-key` |
| `.icp/cli-home/port-descriptors/<port>.json` | Same JSON shape; present in some projects, absent in others. Fallback. |
| `.icp/cache/mappings/<network>.ids.json` | A **name → canister-id map**, keyed by network. Not guaranteed to contain a `root` entry. |
| `.icp/cli-home/identity/…` | Project-local identity store, when present |
| `~/Library/Application Support/org.dfinity.icp-cli/identity/` | User-level identity store; the fallback when no project-local store exists |
| `.icp/<env>/canisters/<role>/<role>.did` | Built canister artifacts, when a project builds per-role |

Verified against two real trees: this repo (`local.ids.json` → `{"fixture": …}`, no
`cli-home/`, descriptor under `cache/networks/local/`) and `toko`
(`toko.ids.json` → `{"root": …}`, with a `cli-home/`).

**Static ids are not sufficient, but they are also not always rooted.** In a canic
fleet like toko, `toko.ids.json` contains only `root` and the rest of the fleet is
created at runtime, so the tree walk is the only way to reach most canisters. In a
plain project like this repo's fixture, the mapping contains the canisters directly
and there is no `root` at all.

So the model is a **forest**: every entry in the mapping is a tree root, and each is
walked for canic children if it has them. A canister without `canic_*` endpoints is
simply a leaf. Hardcoding a `root` key breaks every non-canic project:

1. Read the name → id map from `.icp/cache/mappings/<network>.ids.json`.
2. Call `canic_canister_children` on it, paging with
   `record { offset : nat64; limit : nat64 }`.
3. Each `CanisterInfo` is `record { pid : principal; role : text; created_at : nat64;
   module_hash : opt blob; parent_pid : opt principal }`. `parent_pid` builds the
   tree; `role` labels the node and matches the `.icp/<env>/canisters/<role>/`
   directory name.

Identities live in icp's own store, **not** dfx's. toko's default is `toko-local`,
a plaintext `secp256k1` pem — so `ic_agent::identity::Secp256k1Identity` is the
loader, and the pem's algorithm must be read from `identity_list.json` rather than
assumed.

Canic's error type is `record { code : ErrorCode; message : text }`. The explorer
decodes only `{ message : String }` from it — candid skips unmatched record fields,
so this deliberately avoids coupling to canic's large and evolving `ErrorCode`
variant.

## Architecture

The Rust backend is the only component that speaks Candid or touches the IC. The
frontend receives plain JSON DTOs and never imports an icydb type. That single
boundary is what makes icydb's version churn survivable.

```
React/Vite/Tailwind  ──tauri invoke──▶  Rust backend  ──ic-agent──▶  canister.icydb_query
   (plain JSON DTOs)                    (icydb =0.202.1)
```

### Modules

| Module | Responsibility | Depends on |
|---|---|---|
| `discovery` | Parse `.icp/` into environments, root ids, replica URL, identity | filesystem only |
| `topology` | Walk `canic_canister_children` into a fleet/role tree | `agent` |
| `agent` | Build and cache one `ic-agent` per environment; `fetch_root_key()` locally; load identity pem | ic-agent |
| `sql` | Send `icydb_query(text)` as a query call; decode into `SqlQueryResult` | `agent`, icydb |
| `view` | Convert `SqlQueryResult` into stable frontend DTOs | icydb (types only) |
| `commands` | Tauri command surface | all of the above |

`discovery` reads the filesystem and nothing else; `view` is a pure function with no
IO. Both are fully testable without a replica.

**`view` is the load-bearing module.** It is the only place icydb's shapes are
translated. Each `OutputValue` variant becomes
`{ kind: "ulid" | "principal" | "decimal" | …, display: string }`, letting the grid
right-align numerics, render `Null` distinctly, and truncate blobs without the
frontend knowing icydb exists. When icydb bumps and `SqlQueryResult` shifts, `view`
is the only module that changes.

`topology` degrades gracefully: a canister without `canic_*` endpoints yields a flat
list rather than an error.

Note for `view`: icydb's catalog description structs
(`EntityCatalogDescription`, `EntityFieldDescription`, `EntitySchemaDescription`)
have **private fields with `const fn` accessors** — `entity_name()`, `store_path()`,
`storage()`, `columns()`, `indexes()`, `relations()`, `schema_version()`. They derive
`CandidType + Deserialize`, so they decode fine, but `view` must read them through
accessors rather than field access.

### Command surface

`list_environments`, `list_canisters`, `canister_tree`, `list_tables`,
`describe_table`, `fetch_rows{cursor}`, `run_query{sql}`.

## Read-only enforcement

Two independent layers, with different strengths:

1. **The canister's `readonly = true`** is the real security boundary —
   `icydb_update` and `icydb_ddl` are not generated at all.
2. **The app** calls only `icydb_query`, only via `query_call`, and classifies
   console statements client-side, rejecting anything that is not
   `SELECT`/`SHOW`/`DESCRIBE`/`EXPLAIN`.

Layer 2 is a UX affordance — a fast, clear error instead of a confusing failure —
not a security control. The app must not imply otherwise in its messaging.

## SQL console

Free-form input rendering into the same grid as browsing. Statements are classified
before send, and rejections explain why (e.g. "`INSERT` is not available — this
explorer is read-only"). A `SELECT` with no `LIMIT` gets a default limit appended,
and the UI shows that it was appended — no silent modification, and no accidental
full-table scans against a canister.

## Paging

`Projection` and `Grouped` carry `next_cursor`. Cursors are opaque strings held in
per-tab backend state, driving a "Load more" affordance. The app does not synthesize
offsets or total row counts.

## Error handling

`icydb::Error` decodes with its diagnostic code. Four cases get purpose-written
explanations rather than raw error text:

| Condition | Message intent |
|---|---|
| Canister has no `icydb_query` method | SQL surface not enabled; add `features = ["sql"]` and an `icydb.toml`. Mirrors the recovery hint icydb-cli already emits for this case |
| `SqlIntrospectionDisabled` | Canister was built with `introspection.ic = false` — presented as a configuration fact, not a crash |
| Caller is not a controller | Which identity was used, and that these endpoints are controller-gated |
| Replica unreachable | Which environment and URL were tried |

## Testing

| Scope | Approach |
|---|---|
| `discovery` | Fixture `.icp/` trees → expected environments, root ids, replica URL, identity |
| `view` | `SqlQueryResult` fixtures → DTO snapshots, covering **every** `OutputValue` variant; pure and fast, no replica |
| Statement classifier | Table-driven: statements → allowed/rejected |
| Integration | Real query calls against a local replica running the fixture canister |
| Frontend | Grid components against DTO fixtures |

## Out of scope for v1

Writes, DDL, cross-shard fan-out, mainnet identity management beyond pem loading,
query history, and result export. All additive later; none load-bearing now.

## Known risks

- **icydb version coupling.** `SqlQueryResult` and `OutputValue` shapes change across
  releases (0.184 → 0.202 within the local cargo cache; the repo was pushed the same
  day this design was written). Mitigated by pinning `=0.202.1` and confining
  translation to `view`. Bumping icydb is expected maintenance, not an emergency.
- **Controller-gated access.** The explorer is useful only with a controller identity
  for the target canister. Acceptable for a developer tool.
- **Mainnet schema blindness.** With `introspection.ic = false`, table and column
  discovery is unavailable on IC builds. The app explains this rather than failing
  opaquely; per-canister opt-in is the only fix and belongs to the canister's owner.
